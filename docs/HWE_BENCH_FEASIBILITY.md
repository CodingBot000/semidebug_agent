# HWE-bench feasibility (research, not a measured repair result)

Checked 2026-09-23 against the RTL repair [HWE-bench repository](https://github.com/pku-liang/hwe-bench) at commit `10c78a87e1f92695d78d15b1464a6107dcac8837` (Apache-2.0). This identifies the project described in the V2 plan; another project also uses the name HWE-bench.

The upstream README describes 417 repository-level historical bug cases, including 35 Ibex cases. Its quickstart requires the repository and Harbor dependency, a separately downloaded dataset, per-PR Docker images, generated task directories and the upstream validation harness. [Image documentation](https://github.com/pku-liang/hwe-bench/blob/main/docs/images.md) says the Ibex pull command downloads a shared base image plus every per-PR image referenced by the selected dataset. Generated tasks incorporate each image's baseline SHA, so changing image builds requires task regeneration.

This differs materially from SemiDebug's single-module `case.json` and fixed Icarus/Verilator/Yosys gate. HWE-bench must use its official repository-scale fail-to-pass validation, and an adapter must preserve the host-Codex credential boundary rather than copying authentication into evaluator containers. Subject repositories and dataset assets also require separate redistribution review despite the harness's Apache-2.0 license.

Status: upstream structure and setup reviewed; dataset and images have **not** been downloaded, disk usage has **not** been measured, and no HWE baseline or model case has been run. After ChipBench evaluation, a 3–5 case Ibex pilot would require pinning the exact JSONL revision and selected PR IDs before model calls, downloading only necessary images if the upstream tooling permits, checking official baseline failure and gold pass, then bridging provider proposals to the official harness. If the image/resource cost is excessive, the V2 result report will use ChipBench as its external evidence and state that HWE-bench was not evaluated.
