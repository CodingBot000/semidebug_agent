# Execution and integrity boundaries

- The bundled fixtures are original, trusted HDL. Native mode is for trusted projects only.
- No shell commands or arbitrary manifest build commands. Validated identifier/path syntax prevents argument and Yosys script injection. Symlinks, traversal, extra dependencies and out-of-root paths are rejected.
- No source directory walk in context selection: only explicitly allowed RTL and immutable testbench sources. Gold/evaluator files and split metadata never enter provider requests or temporary agent workspaces. This is an application data boundary, not protection from a malicious user who can modify the Python process.
- Unified diffs must apply exactly to existing mutable RTL, <=2 files and <=40 added/deleted lines. Tests, expected outputs, manifest, assertions, system-task manipulation, force/release, preprocessor/tool directives and hierarchical references cannot be changed. Lexical checks are defense in depth, not a proof against semantically malicious HDL.
- Immutable SHA256 maps are compared before/after validation. The original selected project files are also fingerprinted. Candidate failures do not modify source files. A missing completion marker, nonzero status, critical lint warning, timeout or failed regression cannot become success.
- The subprocess environment does not inherit LLM credentials. Captured output is bounded at 256 KiB per stream; each tool gets a bounded timeout, and the process group is killed on timeout/output overflow and on parent exit.
- `scripts/docker_run.sh` defaults to no network, 2 CPUs, 2 GiB memory, PID limit 128, dropped capabilities, no-new-privileges, non-root user and read-only project mount. Only artifacts are writable. Live mode enables network for the provider. Do not feed hostile RTL to live mode; API credentials in a process/container do not constitute a safe boundary against arbitrary HDL system tasks. Stronger arbitrary-code support requires a separate disposable worker VM/container with no credentials or project secret mounts.
- API keys come from .env/environment; .env is excluded from Git, Docker build context and ZIP. No Codex login credentials are reused. Prompts are not persisted; returned explanation/diff and relevant EDA logs are evidence and may contain source code.
- Package scanning detects common key formats/private keys; it is a heuristic, not a guarantee. Review what is shared. Repository visibility defaults to private.

## Codex CLI mode

The trusted host CLI uses normal ChatGPT login. Authentication storage is never read/copied by the adapter or mounted into EDA containers. Explicit CLI subprocess environment omits API-key/token overrides. Stateless inference uses read-only/ephemeral mode, disables tools and user plugins, and rejects detected tool events. Only manifest-selected evidence reaches the prompt; evaluator gold stays outside inference. Local CLI configuration and model diagnostics can vary with CLI versions; successful completion and valid structured output are still required.
